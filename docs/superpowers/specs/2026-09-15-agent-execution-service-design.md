# M1C-2B Agent 应用服务与执行记账设计

日期：2026-09-15。分类：架构整合。状态：**用户已确认推荐方案；M1C-2B 本地后端实现已验收，尚未部署或接入手机。**

用户已同意继续将任务库、Agent Loop 和预算账本串起来。本书沿用已确认的 [个人设备与云任务规格](2026-09-14-agent-device-tasks-design.md)，补齐每步派发和晚到用量的具体边界；不能用 M1C-2A 的验收代替本批实施。

## 1. 目标和不做的事情

形成可离线验证的完整服务链：认证并接单 → 唯一认领 → 有界 Loop → 授权摘要工具 → 最终结果持久化；每次供应商请求必须有归属明确的预算预留与持久派发许可。

保留既有约束：最多 3 次模型调用、6 次只读工具、接单起总截止 30 秒；结果最长可查询 24 小时、实际本机保存确认后提前清除；凭据 90 天、可撤销、换机共享账户；故障不自动重跑。原始轨迹和连续心率不上传，输入快照不单独保存到云任务表。

本批只做后端库及组合测试：不开放 HTTP、不创建云资源、不配置真实密钥、不请求真实 DeepSeek/Fish、不改 Android/React、不安装 APK、不提交推送。没有生产精确 tokenizer、远程 D1/免费层验收或全 App $2 保证。沿用主代理实现、子代理只读审查及当前工作区。

## 2. 方案选择

| 方案 | 得失 | 决定 |
| --- | --- | --- |
| 小型应用服务＋持久派发标记＋用量收据 | 复用现有模块，明确取消/崩溃时哪些费用必须保留；需少量适配器和账本扩展 | 推荐 |
| 只在 Loop 外包认证和预算函数 | 代码少，但供应商适配器可能先结束等待，晚到用量丢失；无法证明请求尚未发送 | 不满足已确认安全约束 |
| 现在引入完整云工作流/自动重试队列 | 需要云资源和生命周期验证，容易把恢复状态变成重新执行，也需要处理输入持久化 | 不在本批范围 |

“派发许可”不是供应商确认收到了请求，只表示已经越过可能发生计费的边界；不能实现数据库与远程 HTTP 的跨系统原子提交。

## 3. 应用服务入口

新增 `agent-server/src/agent-service.ts`，内部组合现有认证、任务库、Loop、DeepSeek 协议适配器与 D1 账本。配置来自可信宿主：数据库、有效费率、供应商私密配置、精确输入计数器；测试只替换 HTTP transport、宿主时钟和计数器，不替换业务结果。

可信入口形状：

```ts
prepare(authorization, input): Promise<{
  task: CloudTaskView;
  run: (() => Promise<void>) | null;
}>
```

- `prepare` 在首次异步等待前形成独立、规范化、不可变输入快照，再交任务库校验/接单；不能捕获调用方可变对象，或允许之后替换摘要。
- 只有 `accept.created = true` 返回一次性私密 `run` 闭包；同键重试即使看见 queued，也只返回状态，`run = null`。不重建丢失的闭包，不扫描旧任务启动执行。
- `run` 是服务进程内的能力，不是手机响应字段，不可序列化或记录。它在任何 await 前标记已使用；再次调用、首次调用失败都不能重置。随后仍必须通过数据库唯一认领，内存标记不能代替 SQL。
- 真正传给 `runAgent` 的 `taskId` 是云 task ID；保留原 prompt/consent/summaries，不把本机 ID 当作预算任务 ID。预算 request ID 始终为 `cloudTaskId:1..3`。
- `run` 返回 void，不把裸答案直接返给手机。查询、按请求键恢复、取消、撤回和确认继续走持久 DTO，避免绕过终态竞争、结果清理或保存失败。
- 宿主何时持有/执行闭包是未来 HTTP/Workers 层的职责；本批不凭空使用 waitUntil 或建立后台云队列。进程在接单后退出、闭包未运行时，任务按原截止收敛，用户可主动创建新意图，但不能自动续跑旧意图。

## 4. 每步权限、剩余时限与取消

可信执行检查绑定 executionToken 摘要、云任务 owner/原设备、running 状态与原 deadline，使用 M1C-2A 已验证的数据库执行时钟。owner 永远来自记录，不从请求正文或调用方可修改的字段决定。

检查点：

1. 认领后、进入 Loop 前，获取剩余时间；扣除排队和异步查询耗时，剩余不足即停止，不重新获得 30 秒。
2. 每轮模型步骤开始、预算预留之前检查状态；实际预留的 SQL 再次绑定执行权和任务归属。
3. 供应商输入计数/预检完成后、实际 fetch 前通过持久派发门禁；不是在开始 token 计数前就宣布已经发送。
4. 模型返回且费用处理后、执行下一批只读工具之前再次检查。Loop 增加可选可信执行检查钩子，受同一截止和 AbortSignal 约束；无钩子的旧核心用例保持兼容。
5. 最终答案仍经 `finish` 条件写入；取消、撤回、凭据到期或已有终态后，不能返回/保存迟到正文。

本进程通过服务入口成功取消/撤回后，立即通知对应 AbortController；先写数据库，再发本地中止信号，不能假装取消已持久化。其他进程/管理流程的撤销由上述数据库检查阻止后续步骤；不增加频繁后台轮询，不承诺远程请求瞬时停止。原设备到期不允许换一枚凭据继续旧执行。

数据库校验失败时停止后续模型/工具，不用缓存授权继续。若无法可靠读取或写入终态，可信执行入口只报告静态 `unavailable`，不返回裸结果或编造 completed；已有任务由恢复查询按原截止收敛。沿用现有静态错误类别，不为了本批建立通用错误框架。

## 5. 持久派发证明与安全释放

通过新的增量迁移扩展预算记录，不改写旧账：新增执行权摘要、派发状态和费率有效期快照。旧 M1C-1 记录保留空执行关联，不得拿来派发新 Agent 请求或当作“确定没发送”自动退款。

新执行绑定预算的派发状态为：

```text
prepared ── 原子派发门禁 ──> may_have_dispatched
    └──── 原子封闭/释放 ──> closed_not_dispatched
```

`createD1Budget` 增加可信执行绑定选项；新服务必须使用它，旧独立用例保持原接口行为。预留行一次性绑定 owner、云 task ID、request ID、execution hash，不能先插入没有归属的“临时预留”再补身份。

派发门禁必须在同一 SQL 决策点确认：执行权匹配、原设备有效、任务仍 running、数据库时间未过 deadline/费率期限、预留属于同一 owner/task/request、预算未释放、账户未熔断、派发状态仍 prepared。只有首次 `prepared → may_have_dispatched` 成功的调用可以进入 fetch；超时的门禁 Promise 晚到成功也要先检查 AbortSignal，不能晚发网络请求。

释放和“封闭未发送许可”必须原子发生。只有成功将 prepared 封闭为 closed_not_dispatched，才能把对应尚占用的额度释放；延迟回来的发送流程不能再通过门禁。不能仅凭核心传来的 `not_dispatched` 字符串或“手机已取消”释放已越过派发门禁的预留。

核心已经进入 ModelPort 但计数/预检失败时，新的绑定链路可凭 prepared 状态原子封闭并释放；这不同于旧独立适配链的保守 uncertain 行为。若标记已经是 may_have_dispatched，则即使 fetch 尚未来得及发出、随后超时或进程退出，也保留全部未知费用，不重试、不自动退款。

## 6. 有效用量的独立收据通道

当前代码证据：Loop 在取消后不再走成功结果的用量解析；DeepSeek 适配器自身也会取消正文读取并结束 Promise.race。因此只在外部包装 Loop 不能保证所有已解析用量进入账本。

DeepSeek 适配器新增两个可信内部钩子，旧独立调用保持可选兼容，新服务必须接入：

- `beforeDispatch(requestId, signal)`：实际 fetch 前取得一次性持久许可。
- `onUsage(requestId, usage)`：完整、有效用量归一化后立即进入独立记账通道；该通道不以任务仍 running、凭据仍有效、用户仍愿意看答案为前提。

用量记录必须绑定当前执行和确切 reservation，不接受手机提供的 request ID/usage 声明。回调只接收整数 token 数，不携带 prompt、原始响应、推理或 API 错误正文。

新增只保存最小费用证据的 `agent_usage_receipts`：reservation ID、输入/输出 token、接收时间及已应用标记。先持久化验证后的用量收据，再调用现有幂等实际结算；结算完成后确认收据。进程在两步间退出时，维护流程只重放记账，不重放模型。

- 相同收据幂等，重复结算不增加消费。
- 同一 reservation 出现不同有效用量时，保留首条证据并持久熔断账户，报告冲突；不能静默覆盖、取较小值或任意挑选账单。
- 有效 usage 但模型内容非法，仍先记账，然后停止任务。
- 确实已取得并验证的 usage，即使 Loop 已返回取消/超时，也尝试持久保存和结算，不能因为 AbortSignal 已中止就跳过。
- 已取消读取、未完整取得或未能验证的 usage，无法凭空恢复，继续保留 uncertain 待供应商账单核对。不为获得账单而无界读取取消后的响应。
- 收据写入本身失败或进程在写入前退出时，没有“已持久保存”的证据；保留预留且停止，不能宣称所有费用都能自动恢复。实际 Workers 生命周期保证和外部账单对账仍是上线门禁。

核心原有结算与独立收据通道可能竞争；实际用量结算必须优先且幂等，后到 uncertain/not_dispatched 不得把 settled 改回未收费。旧预算测试需要原样保留，并补充新绑定模式的竞争测试。

## 7. 恢复只恢复状态和账务

新增可信维护入口，每次有界处理最多 100 条记录并返回计数/后续游标，不读取或展示任务正文，不调供应商。

- 已有用量收据未应用：调用幂等结算并确认收据。
- 任务已结束/超时或原设备失效，预算仍 prepared：原子封闭发送许可并释放可证明未发送的预留。
- may_have_dispatched 且没有有效收据：保留未知费用，必要时收敛到 uncertain；不按经过了多少分钟自动释放。
- 已取消任务的有效晚到收据：继续结算，不恢复答案。
- 无执行关联的旧账本记录不套用新的未发送证明，保持原规则。

不设计重新排队、租约抢占或自动续跑；不从没有数据的本进程任务表推断其他进程已崩溃。维护与迟到派发竞争必须通过 SQL 状态转换解决，不能依赖进程内锁。

实际定时调用、失败告警、远程 D1 与 Workers 退出处理不在本批部署，只提供并验证这些维护操作。
