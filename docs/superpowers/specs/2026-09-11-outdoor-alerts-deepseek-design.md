# 户外误报、心率提醒与 DeepSeek 陪伴句设计

日期：2026-09-11

状态：用户已审阅通过并要求开始工作；按心率、数据状态／BLE 通知、DeepSeek 三批实施。

代码基线：仓库 HEAD `f1eba9c`；当前手机生产语音实现为 `bb461ea`。

## 1. 目标与已确认决定

先处理本次三项户外反馈，再继续已有 API 状态面板计划。用户已认可：

1. 区分手机定位弱、心率停更和真正的蓝牙连接异常。
2. 新增独立心率警戒阈值；首次保持连续超标 10 秒后提醒，高心率重复提醒默认间隔 120 秒并可修改；短暂恢复不能绕过间隔。
3. 真实蓝牙异常持续 10 秒才播报，同次故障不反复播报。
4. DeepSeek 负责可选陪伴句，Fish 仍负责流萤声音；文字等待最多 2 秒，紧急提示始终立即本地。
5. 新密钥由用户在手机配置入口自行填写。开发和模拟测试不依赖真实密钥；不使用聊天中出现过的凭据。

本文中的提醒参数是产品行为，不是对用户个人医学安全心率的判断。

## 2. 证据与非目标

本次户外日志分进程统计：Fish 播放完成 12 次、内置完成 26 次、系统语音 0 次，公里播报 3 次成功；高心率提醒 25 次。四次「手环数据中断」实际由距离数据陈旧触发，附近仍有 B5 写入成功，未记录跑中 BLE 断开或重连。手机只读检查显示文字 AI 关闭、未配文字密钥，Fish 配置完整。

详细取证见 [夜间实测交接](../../handoffs/2026-09-10-night-outdoor-feedback.md)。这些证据不能证明所有网络和底层射频状态永远可靠。

本轮不做：

- 不更换或重新生成 14 条已验收音频，不改变公里数字和整句合成方式，不恢复系统 TTS。
- 不修改 B5 协议报文、START/STOP、同步频率、重连算法、GPS 距离算法、千卡来源或 Health Connect。
- 不建设多供应商平台、电脑代理服务、自动付费巡检或定时聊天。
- 不实现完整 API 状态面板和跑前检测；本轮只提供 DeepSeek 配置状态与安全诊断。已有计划需在本轮结束后按 DeepSeek 接口重新核对，不能直接执行其中旧 Anthropic 假设。
- 不借接入 DeepSeek 恢复旧的紧急文案预生成、每公里额外分析或第二次播报。

## 3. 选定方案及取舍

### 3.1 数据异常：按来源判定

选择分别使用定位新鲜度、心率新鲜度和真实 BLE 生命周期。只改「手环」字幕不能纠正错误判断，也会与内置音频不一致；简单拉长旧 `data_stale` 冷却仍然会误报，均不采用。

### 3.2 心率：独立警戒值与专用冷却

选择独立警戒值及高心率重复间隔，保持训练分区计算不变。不通过提高最大心率减少提醒，也不只调全局同句间隔来掩盖固定 30 秒规则。

### 3.3 DeepSeek：复用官方兼容格式

选择 DeepSeek 官方 Anthropic 兼容接口，保留现有 system/messages 请求和文本块解析思路。另写 Chat Completions 适配也可行，但会增加一套请求和解析，本轮无此必要。

服务地址、模型、凭据来源和诊断提供方必须明确属于 DeepSeek；兼容请求格式不代表请求发给 Anthropic。

## 4. 心率提醒行为

### 4.1 设置与兼容

| 字段 | 默认／合法范围 | 用途 |
| --- | --- | --- |
| `maxHeartRate` | 保留现值及现有校验 | 训练分区参考，不因本轮自动提高 |
| `hrAlertThresholdBpm` | `null` 或整数 80–240 | `null` 为自动沿用当前分区门槛；非空为独立警戒值 |
| `hrAlertRepeatIntervalSec` | 120；整数 30–300 | 仅高心率 `hr_z5_danger` 的重复提醒间隔 |
| `ttsMinIntervalSec` | 保留现值与现有范围 | 原有同句语音节流，仍参与过滤 |

自动门槛为使旧分区算法进入 Z5 的最小整数心率，即最大心率的 90% 向上取整；需以边界测试保持与当前算法一致。现值 180 对应 162，升级不变。设置页显示「自动（当前 162 bpm）」这类实际计算值，不能把「自动」宣传成个性化医学评估。

用户手动填写警戒值后不再随最大心率改变；清空并保存恢复自动。非法值不得静默裁剪。新设置缺失时采用上述默认，不改旧记录或其他偏好。

警戒值与专用间隔属于开跑时冻结的配置；跑中或暂停时保存，明确提示「下次跑步生效」。语音总开关保留现有即时生效行为。

### 4.2 触发、持续与恢复

- 仅 RUNNING 状态评估高心率提醒；使用新鲜、非空的平滑心率，达到或超过警戒值才算超标。
- 首次连续超标至少 10,000 毫秒才产生事件。不得仅因累计收到 10 帧就声称已经持续 10 秒。
- 连续性和专用冷却使用可注入的单调时钟，Android 实现覆盖休眠；系统时钟前后调整不得绕过间隔。时间戳和日志日期仍使用现有墙上时钟。
- 任一帧低于门槛、心率陈旧／为空、流水评估间隔超过 2,000 毫秒或进入暂停，均清除连续超标计时；恢复后重新满足 10 秒条件。
- 从上一次高心率事件产生时起计算 120 秒或用户设置的间隔。持续超标可在到期后再提醒；冷却期间的短暂恢复、暂停／恢复、跨公里、设置页往返都不能清零该计时。
- 因冷却到期不应自动播报旧事件，必须同时满足当前连续超标条件。
- 语音关闭或总线丢弃的事件不在以后补播；文字提示与现有总线策略保持一致。
- `hr_rapid_rise` 的独立判定、60 秒冷却和紧急优先级保持不变。本轮不把不同告警混成一类，不让新冷却压制另一种首次告警。
- 新跑步重置本会话提醒状态。进程恢复时不回放旧提醒，首次重新满足 10 秒连续条件后才可提醒。本轮冷却为进程内会话状态，不新增跨设备重启的提醒持久化，也不宣称进程重建后仍严格继承上次提醒的剩余间隔。

实现只调整必要的规则参数与计时接口，不整体重写规则引擎。新冷却不得被旧固定 30 秒门禁或第二套独立冷却意外叠加。

## 5. 三种数据状态与手环通知

### 5.1 独立状态

在快照中增加只读 `dataQuality`，与现有 `wearable.state` 分开：

- `gps`：`waiting`、`fresh`、`stale`。本会话从未取得有效距离样本为 waiting；以后沿用现有定位新鲜度判定。
- `heartRate`：`not_available`、`waiting`、`fresh`、`stale`。未支持手环为 not_available；尚无有效心率为 waiting；曾取得心率后依据独立心率新鲜度判定。

这些状态只表达当前数据是否可用，不推导运动健康结论。暂停时不以冻结的跑步指标判断 GPS 断流；心率使用现有暂停心率监测来源，BLE 使用独立连接状态。

| 情况 | 屏幕 | 声音 |
| --- | --- | --- |
| GPS 陈旧，BLE 正常 | 定位提示；配速不可用，距离不虚增 | 不播「手环数据中断」 |
| BLE 就绪但心率陈旧 | 心率暂未更新，显示无有效心率 | 不播连接中断，不触发高心率提醒 |
| 从未获得定位／心率 | 等待定位／等待心率 | 不把初次等待说成中断 |
| 真实 BLE 异常短于 10 秒 | 如实显示连接状态 | 不播中断 |
| 真实 BLE 异常持续至少 10 秒 | 手环连接异常 | 本故障最多提交一次中断提示 |

多个数据问题可同时显示在各自指标／状态区域，不互相覆盖已有高优先级安全提示。

### 5.2 真实 BLE 事件来源

`ConnectionState.CONNECTING` 也用于正常开跑握手，不能单凭该值当作真实断开。预连接 PreparedPrivate 与运动就绪 Ready 同样不能混用。

从已有 Supervisor 输出只读、带代次的链路观察信息，区分预连接／初次握手、运动就绪、真实故障恢复及主动结束；不改变 Supervisor 的决策或 BLE 报文。只有本会话曾达到运动就绪，之后发生真实故障或由故障引起的重连，才启动 10 秒资格计时。初次连接失败只显示连接未完成，不冒充「已连接后中断」。

新增纯 Kotlin 的手环通知状态组件，由 Coordinator 的连接观察与单调定时器驱动；它独立于 GPS 每秒流水，因此 GPS 没有新样本、跑步暂停时也能正确工作。

### 5.3 防抖、恢复与取消

- 异常必须连续满 10,000 毫秒；正常开跑、用户在非跑步状态主动断开、结束清理均不触发。
- CONNECTING/ERROR/DISCONNECTED 之间的故障恢复流程属于同一故障，不能每次切换就再播。
- 一旦恢复运动就绪，立刻取消资格定时器及尚未开始的中断播报；如果中断音频正在播放，只停止这一条，不打断其他提示。
- 就绪稳定 10 秒后才解除该故障的「已通知」标记。短暂恢复再失败不会制造一串新故障；如果此前尚未通知，再次异常仍须重新连续满足 10 秒。
- 每个故障代次最多提交一次。总静音、优先级拒绝或播放失败均不进行迟到补播，屏幕仍显示故障。
- 新跑步、停止、恢复流程更换代次以及 Coordinator 关闭时，取消旧定时器和该故障的语音任务。所有迟到回调必须检查跑步代次与故障代次。
- 应用进程恢复不重放此前断开；先建立新观察基线。若未恢复就绪，只显示连接状态，重新就绪后的新故障才可产生通知。

### 5.4 复用已验收音频

移除「距离陈旧触发 `data_stale`」的指标规则派发。实际 BLE 故障通知复用已有 `data_stale` 文案与音频「手环数据中断，请检查」，不重新生成资源。

该连接通知直接使用内置流萤音频，不等待 DeepSeek 或 Fish，保持 APP 优先级，不抢占紧急心率提示。总线提供按该通知身份取消的最小能力，不能为了撤销连接通知清空整条语音队列。

语音覆盖测试应将新通知工厂纳入真实触发源清单，证明原音频仍被使用；日志另记明确原因 `ble_link_lost` 和故障代次，避免与旧版距离误报混淆。不能通过让旧错误规则和新通知同时存在来保持测试通过。

## 6. DeepSeek 配置与调用

### 6.1 手机私密入口

设置页增加「AI 陪伴」开关、DeepSeek 配置状态和「配置／更换 DeepSeek 密钥」按钮。Web UI 的按钮只发出无凭据的命令 `settings.configureDeepseek`，由当前 Activity 打开原生遮罩输入对话框；Web 页面及桥接结果不接收密钥原文。

- 输入框不自动回填已保存密钥、不提供显示原文按钮、不记录日志、不使用可恢复保存状态；关闭、取消或保存成功即清空输入状态。
- 对话框显示期间禁用截屏和最近任务预览敏感内容，退出后恢复之前窗口标志。关闭输入建议／自动填充，不主动读取剪贴板。
- 新凭据通过独立 `DeepseekCredentialsStore` 保存于 App 私有、排除系统备份的目录，不混入原 `settings.preferences_pb`、运行数据库、Web localStorage 或项目文件。
- 本轮采用 Android 应用沙箱及排除备份，不宣称已实施 Keystore 加密。不能防御已获 root 或调试权限的设备访问；不修改现有 Fish 凭据格式或整体备份设置。
- 只接受去掉首尾空白后非空、长度至多 512 且不包含内部空白或控制字符的输入；不凭历史令牌前缀猜测完整合法格式。失败保留旧值，不输出原始异常。
- 对话框可取消；替换操作不改变 Fish。暂不提供批量导入、导出或读取现有密钥功能。
- 不在 RUNNING/PAUSED/恢复会话过程中打开凭据对话框；原生入口与桥接同时校验，保存时也须与开跑互斥复核。开关仍可关闭以取消正在准备的 AI 语句。

设置快照只新增 `deepseekApiKeyConfigured` 布尔值；`llmEnabled` 继续作为 AI 陪伴开关的契约字段，但持久化改用独立的 `deepseek_companion_enabled` 键，缺省为 false。旧 `llm_enabled` 不自动继承，避免旧开关为 true 时填入新密钥即意外启用。未配置时不可开启，并显示填写入口；新开关为 true 但凭据缺失时也按关闭处理。保存密钥不自动开启开关、检测或试听，替换密钥不改变已有的新开关值。

旧 `llmApiKey` 仍属于旧 Anthropic 设置，不自动迁移为 DeepSeek。旧快照字段保留兼容但不得用于 DeepSeek 的已配置判断；原生旧 Claude 输入入口需调整到同一个 DeepSeek 对话框，避免用户输错服务。

状态文案严格区分「未配置」「已配置，AI 陪伴关闭」「AI 陪伴已启用，尚未验证连接」。保存成功不代表请求成功。完整最近调用状态面板仍由后续已批准项目处理。

### 6.2 固定调用边界

- HTTPS 目的地址固定为 `https://api.deepseek.com/anthropic/v1/messages`，模型显式 `deepseek-flash`，`thinking.type=disabled`，非流式，`max_tokens=100`。
- 使用 DeepSeek 专属、请求接纳时捕获的配置快照，不能经旧 `LlmConfig.apiKey` 全局字段转交给 Anthropic 客户端；凭据对象的调试字符串不得包含原文。禁用自动重定向和应用级自动重试，凭据仅发往固定 DeepSeek 目的域名。
- 保留当前短陪伴提示词的约束：不重复或修改固定核心，不新增真实数字、健康判断和运动指令；没有额外通用聊天历史。
- 普通提醒仅发送固定核心与必要的语气选择；公里提醒允许发送当前代码已有的分段／累计摘要。不得附带 GPS 坐标、路线、设备标识、联系人、密钥或整个数据库。
- 最多读取 64 KiB 响应；只接受成功状态、自然完成的有效文本块，过滤空值、换行、结构化输出、重复核心、新增数字及超过 50 字的结果。过滤不通过即不附加鼓励，不播推理内容、错误页或截断句。
- Prompt 与有限文本过滤不能保证理解任意自然语言，故生成内容只作陪伴，不作为健康决策来源；实际健康判断仍由确定性规则控制。
- 请求取消必须调用网络取消，关闭响应体；迟到结果不得开播或更新新的配置状态。错误只映射为认证、限流、网络、超时、协议／内容无效等安全类别，不记录响应正文、请求正文、Authorization、密钥长度或密钥片段。

官方依据（2026-09-11 已只读核对，非本 App 真机认证）：[接口首页](https://api-docs.deepseek.com/)、[兼容接口](https://api-docs.deepseek.com/guides/anthropic_api)、[Chat 参数及非思考模式](https://api-docs.deepseek.com/api/create-chat-completion)。开始实施时复核兼容接口的实际字段，不以模型名称别名映射代替显式模型配置。

### 6.3 与现有语音策略的组合

| 场景 | 处理 |
| --- | --- |
| 紧急心率提醒 | 内置流萤立即播放，0 次 AI/Fish 请求 |
| 已确认的 BLE 中断通知 | 内置流萤，APP 优先级，0 次 AI/Fish 请求 |
| 普通／公里且 AI 关闭或未配置 | 跳过文字请求，仍按既有规则尝试 Fish 合成核心 |
| DeepSeek 成功且句子有效 | 核心＋陪伴句一次交给 Fish 整句生成 |
| DeepSeek 失败或 2 秒到期 | 取消文字请求，仅用核心继续 Fish，不追加迟到句 |
| Fish 失败／准备超时 | 普通提示回内置核心，公里静默跳过 |
| 语音总开关关闭 | 不播报，不因开关恢复而补播旧事件 |

2 秒文字等待包含在既有总预算内；普通 8 秒／公里 15 秒从 SpeechBus 接纳起算，排队、文字、合成和媒体准备都扣除。不得通过接入新提供方重新开始计时，也不通过增加重试或自动预热制造额外付费请求。

## 7. 实现边界与契约

| 层 | 必要调整 |
| --- | --- |
| 设置与配置 | 两个心率字段、缺省／范围／空值语义、开跑冻结；DeepSeek 凭据独立仓库及仅布尔快照 |
| 指标与规则 | 保留 GPS/心率独立新鲜度；高心率独立阈值和单调冷却；移除距离到手环音频的错误映射 |
| BLE 观察 | 增加只读就绪／故障及代次观察，不修改传输、重连和会话控制行为 |
| Coordinator | 独立数据质量快照、手环故障通知定时器与取消、配置入口事件 |
| 语音与文字 | DeepSeek 专属适配、内置连接通知、仅定向取消该通知；已有整句合成和焦点流程复用 |
| 双端桥接与界面 | 新字段、无凭据配置命令、严格校验、原生输入；设置页与跑步数据状态一致 |
| 诊断 | DeepSeek 安全结果、明确 BLE 通知原因；不收集密钥、响应正文或路线 |

新增字段与命令须在 Kotlin wire/codec、前端类型/Zod、契约文件、样例、模拟桥接和测试中同批更新。保持 contractVersion 1 的同包协同方式，新增明确能力标识，严格校验未知字段；不可用全局宽松解码掩盖两端不一致。新输入命令无参数，不接受 Web 传入的原始密钥。
